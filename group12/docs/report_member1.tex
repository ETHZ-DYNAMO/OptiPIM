\section{Implementation and Experimental Setup}
\label{sec:setup}

\subsection{Toolchain}
We use the authors' public flow (ETHZ-DYNAMO/OptiPIM, commit 9be8f9a),
forked into our group repository. The flow has three parts: \texttt{pim-opt},
an MLIR pass built on LLVM (commit 39048b69) that reads one layer in the
\texttt{linalg} dialect, builds the integer linear program (ILP) of the paper,
calls Gurobi and writes the resulting mapping as a trace file; a Python
analytical model (\texttt{validation/analytical\_modeling}) that scores a trace
with the paper's cost model (Eq.~17--20); and a modified Ramulator2 that
replays a trace with PIM commands and reports \texttt{memory\_system\_cycles}.

We built the flow on Ubuntu 22.04 under WSL2 on a Windows laptop
(6 logical cores and 11\,GB of RAM given to WSL, Ubuntu 22.04.5, g++ 11.4.0). Building LLVM, \texttt{pim-opt} and
the simulator took about 4\,h\,15\,min (LLVM and \texttt{pim-opt} about 4\,h, the simulator about 15\,min more, from file timestamps). We used Gurobi 13.0.3 with a free academic
licence, while the paper used 11.0.3. The repository's CMake module only
searches for Gurobi 11.0 and 12.0, so we exposed the 13.0 library under the
12.0 name; no source code was changed. With Gurobi 13, presolve wrongly
reported the $3{\times}3$ convolutions C1 and C2 infeasible on HBM-PIM at 32 banks
(the model solves at 8, 16, 17 and 20 banks); we therefore solve the HBM-PIM
runs with presolve disabled (\texttt{Presolve 0}), which gives a proven optimum. A Dockerfile in the repository
reproduces the same build for members on macOS.

\subsection{Operators and targets}
Following the reduced scope, we map five single operators rather than full
networks (Table~\ref{tab:ops}): three 2D convolutions from ResNet-50 and two
matrix multiplications from BERT, taken from the layer files shipped in
\texttt{nn\_models/} with the number of banks set to 32. C1 is the ResNet-50
layer the paper analyses in its Fig.~12. Each operator is mapped onto two
targets: HBM-PIM (\texttt{--target-device-type 1}, arch file
\texttt{data/hbm\_pim.json}) and SIMDRAM (\texttt{--target-device-type 0},
\texttt{data/dram.json}), both with 16-bit values.

\subsection{ILP configuration}
All runs use the paper's full method: flexible indexing
(\texttt{--trans-coeff-method 4}), the paper's input-counting estimate
(Eq.~11, \texttt{--number-counting-method 0}) and the PIM cost objective
(\texttt{--obj-method 0}). One script, \texttt{group12/scripts/run\_all.sh},
solves all ten operator--target pairs, stores each mapping and the full
Gurobi log, and records the wall-clock and Gurobi solve times
(Table~\ref{tab:solve}). Solving took between 1.1 and 181
seconds per operator, compared with 1--209~s reported by the paper on a
16-core server. A rerun from a fresh clone of the repository produced \fillin{identical mappings / mappings with identical objective values (Gate 2)}.

\subsection{Solver objective versus analytical model}
\label{sec:objcheck}
We scored every OptiPIM mapping with the authors' Python analytical model and
compared it with the objective value of the ILP (Table~\ref{tab:obj}). On
SIMDRAM the two agree within 5--32\%. On HBM-PIM the model's cost is 2--3$\times$
the solver objective for the convolutions and 70--110$\times$ for the matrix
multiplications. We have not identified the cause; one possibility is that
the model's total includes the one-time weight loading, which the ILP
objective may omit. For C1 on HBM-PIM the model gives 870{,}912 cycles for the
OptiPIM mapping and 29{,}546{,}496 for the authors' weight-parallel heuristic
mapping, a 34$\times$ reduction that comes almost entirely from input
loading (225{,}792 versus 28{,}901{,}376). The paper reports a larger gap
(about 100$\times$) for this layer; we did not verify the units of its figure.

\subsection{Analytical model versus simulator}
\label{sec:simcheck}
We replayed the OptiPIM mappings in the authors' Ramulator2 simulator and
compared the cycle count with the analytical model (Table~\ref{tab:sim}).
On HBM-PIM the model is within 2.1\% of the simulator for all three
operators checked, which agrees with the paper's claim that the model tracks
the simulator closely. On SIMDRAM the model consistently underestimates the
simulator, by 38--76\%; we did not find the cause. Note
that the solver objective differs from both (Table~\ref{tab:obj}), so the ILP
objective is not itself a cycle count.

\subsection{Mapping found for C1}
On HBM-PIM the ILP maps C1 with $Q{=}2$ and $C{=}16$ across the 32 banks, $P{=}28$,
$Q{=}2$, $C{=}8$ across columns, and $K{=}128$, $Q{=}7$, $R{=}S{=}3$ in time. The paper's
Fig.~12(b) mapping differs (16 banks, $C{=}16$); we did not score the paper's
mapping, so we make no claim that the two have equal cost.

\section{Limitations of Our Setup}
\label{sec:limits}
\begin{itemize}
\item \textbf{Few simulator points.} C1 and C2 were not replayed in Ramulator2 (their traces take very long), so the model-versus-simulator check covers C3, M1 and M2 only.
\item \textbf{No real hardware.} All cycle counts come from the analytical
model and the authors' Ramulator2-based simulator, which model HBM-PIM and
SIMDRAM timing but not every effect of a real chip.
\item \textbf{Different solver version and machine.} We used Gurobi 13.0.3 (with presolve disabled for HBM-PIM) on
a laptop instead of 11.0.3 on a 16-core server, so absolute solve times are
not comparable, and an ILP with several optimal solutions may return a
different mapping with the same cost.
\item \textbf{Five operators, one bank count.} We evaluate five single layers
at 32 banks and 16-bit precision only; the paper sweeps whole networks and
several memory sizes.
\item \textbf{Our own heuristic.} The weight-parallel baseline is our
reimplementation from the paper's description (Sec.~6.4.1), checked against
the heuristic trace files the authors ship, not the authors' original code.
\item \textbf{Arch file choice.} The authors' scripts use
\texttt{data/hbm\_pim.json} in one place and \texttt{data/dram.json} in
another for SIMDRAM; we use \texttt{hbm\_pim.json} for HBM-PIM and \texttt{dram.json} for SIMDRAM.
\end{itemize}
